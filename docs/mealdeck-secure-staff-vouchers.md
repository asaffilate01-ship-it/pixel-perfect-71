# Secure staff voucher — reviewed source candidate

## Owner request and implementation choices

A staff member enters a single-use code immediately before paying on the MealDeck website. The canonical server quote deducts 50% of eligible items and extras, including choices and upgrades. Integer-pence rounding keeps the amount due rounded up to the nearest penny when the subtotal is odd. The Stripe minimum payable amount of 30p is preserved. Delivery remains subject to the existing postcode/radius checks and £15 minimum **after** the discount; no delivery fee is discounted. Collection and kerbside are supported. The initial scope is the independent Luton kitchen and direct, registered staff single-payer website orders. Guest, marketplace, cash, terminal, separate/shared group and WhatsApp checkout are not eligible. No discount stacking.

Each code is assigned to an active staff identity with an existing verified member profile; a different person cannot use it even if they obtain the code. Managers with current scoped owner/admin role and both staff.manage and finance.manage issue or revoke vouchers from Staff access. Default validity is 7 days; configurable 1–30 days. No universal code, client-supplied percentage, public code list, Stripe promotion code, or automatic refund reactivation. These are deliberate conservative release choices, not claims of previously approved staff benefit terms.

## Database and payment boundary

The explicit operation at deploy/mealdeck/operations/20261127_staff_vouchers.sql starts disabled, refuses an unrelated or unreviewed installation, and preserves the reviewed materializer except for the guarded discount branch. It adds private RLS-enabled tables and explicitly revokes all direct API role access. Only service-role RPCs can request a voucher quote after verified Auth; only scoped authenticated managers can issue, list or revoke. The random code has 122 random bits and is returned once; only SHA-256 digests are stored. The list contains status, assignee, timestamps and payment evidence, not raw codes or digests. Do not log request bodies, RPC responses or issue codes in analytics, error tracking, session replay or screenshots.

Applying a code creates a fresh canonical member quote; normal menu stock/pricing, packaging, notes, identity, kitchen and payment gates remain mandatory. Ten valid-format attempts per account/scope per ten minutes are counted in a private database row even for rejected guesses. Rate-limit state is not a substitute for entropy or account verification. A code remains unconsumed while reviewing or refreshing an unpaid quote. On first successful **payment preparation**, a row lock and unique binding consume it in the same transaction that creates the canonical order/payment record. Concurrent quotes cannot consume it twice. A retry of an already prepared original payment recovers the original order; no new discount is generated. Stripe receives the frozen net amount, without an additional coupon.

Consumption is deliberately fail-closed: abandonment, expiry, refund, cancellation or provider failure does not automatically release a used code. Reissue only after an authorised manager reconciles the original payment outcome. Existing prepared payment sessions and verified webhooks remain governed by the unchanged payment authority. Ordinary quotes do not use voucher pricing. Disable the private database setting to stop new issuance/redemption; the web flag also hides and blocks new application. Do not disable ordinary payment reconciliation.

## Deployment gates

This is an uninstalled source candidate, not a statement that the live system supports vouchers. Confirm the correct independent MealDeck installation (never Dishbee), materializer signature/hash, role permissions, quote extensions and payment/receipt behavior. Run the PGlite test suite, PostgreSQL 17 test suite including the concurrent two-connection race, application tests, lint, TypeScript and production build. Compare current hosted function definitions and review the proposed patch with the database owner before applying the complete atomic operation; do not bypass its definition guard. Review RLS/ACLs and run database advisors. Run a test payment in a disposable environment, including repeated clicks, expired/revoked/disabled staff codes, discounts on odd pence, removed/reapplied codes, stock changes, delivery minimum, Stripe session recovery, KDS/receipt and refund handling. Check real mobile/tablet/desktop UI and accessibility. Verify no request/response secrets are collected by monitoring. No real charge is required to test code.

Only after these gates, set private database setting enabled=true as the verified database owner, and set MEALDECK_STAFF_VOUCHERS_ENABLED=true on the server. The environment value defaults to false. Do not expose either the owner/service-role key or voucher hashes to staff clients. Issue real codes only through the authorised Staff access panel. Keep audit and rate-limit retention under an approved privacy schedule. No code is active by merging source alone.

### Issuance recovery
Each manager issuance has a unique request UUID scoped to that issuer. Repeating the same request with the same staff member, location and validity returns only the original record ID and expiry, not the secret code. A different payload with the same request is rejected. The UI keeps a failed request available for explicit retry and does not silently create a replacement. The audit list also shows issuer and revoker IDs. A reload loses the transient request ID, so review the audit and revoke a lost unused code before intentionally issuing another.

### Rejected voucher UX
An unsuccessful voucher application keeps the prior reviewed server quote available; its review acknowledgement is cleared, and the raw code is cleared from the input. The user must explicitly confirm the previous total again or enter another voucher. Only a successfully verified replacement quote creates a new checkout attempt identity. The UI refuses a second voucher application while a discounted quote is displayed; remove it or refresh without a code before applying another.
