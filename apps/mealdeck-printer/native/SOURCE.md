# Native printer protocol provenance

The fixed Binder adapter is copied from the unchanged MealDeck Printer Setup app in `../mealdeck-printer-probe/native/`. Its source and reviewed public protocol are documented in that app and `docs/mealdeck-senraise-printer-status.md`. The owner confirmed that the published setup sample physically printed on the H10S on 7 November 2026.

The companion retains the exact explicit service identity, descriptor, service-version transaction and bitmap transaction. Version 0.2.2 renders the complete receipt as one immutable shared-memory bitmap, at most 384 × 16,000 ARGB pixels. Its ordinary Bitmap Parcelable is prepared and bounded to 750,000 bytes before `begin_send`, with a required shared-memory file descriptor. Exactly one bitmap transaction is permitted for that prepared receipt, followed by one fixed `nextLine(4)` transaction within the same dispatch. No cut, arbitrary byte, remote-content or alternative transport API is exposed. Returned Binder calls mean `sent_unconfirmed`, never proof of physical paper.

Android's public [`Bitmap.asShared()`](https://developer.android.com/reference/android/graphics/Bitmap#asShared()) API has been available since API 31 and returns an immutable bitmap backed by shared memory for efficient Parcelable transfer. The app requires API 33. The original mutable allocation is recycled only when it differs from the returned shared bitmap; the latter and its prepared parcel remain owned until the Binder worker exits, including after a UI timeout.

The additional operation is from the same [pinned generated interface](https://github.com/mawlood-fareq/capacitor-senraise-printer/blob/7e2c4e2e6dde6872a239c6cb00fa209317078e45/android/src/main/java/recieptservice/PrinterInterface.java): `TRANSACTION_nextLine = FIRST_CALL_TRANSACTION + 8`, or transaction 9. Its parcel contains only the same interface token and a fixed integer 4, followed by the ordinary synchronous exception reply. The [pinned receipt example](https://github.com/mawlood-fareq/capacitor-senraise-printer/blob/7e2c4e2e6dde6872a239c6cb00fa209317078e45/README.md) uses four feed lines after its final QR. This narrow implementation exposes no line-count control to the WebView or receipt data.

The bitmap and final feed share the same durable attempt, worker slot and no-retry rule. An unsupported feed, exception, expired continuation or uncertain result holds that original attempt; it never retries the image or silently falls back to bitmap-only output. The original 180-pixel white raster tail remains after the footer and is separate from the small PAID-to-promotion gap. The public protocol has no per-receipt physical-completion callback; `beginWork`/`endWork` names are not treated as evidence of a drain or completion barrier.

This removes the companion's consecutive 384-pixel strip calls and the missing explicit end feed. It does not prove that the H10S service accepts every tall immutable image: the setup observation established one 256 × 600 sample. Android emulator checks exercise the raster, standard Parcelable protocol and bitmap/feed ordering against a recording Binder, never the vendor service. Actual-device completion must be observed on the H10S before claiming that the reported partial-paper problem is resolved.
